# 扫雷 AI（Windows 高级局 30×16）

用 **UIA 无障碍接口**读盘 + **纯逻辑求解**决策 + **UIA/鼠标混合**执行的 Windows 扫雷自动化。
单步约 **100 ms**，能完整自动通关一局；带深色 GUI 控制台，可打包成单文件 exe 迁移到任何 Windows 电脑。

## 特性

- **感知**：走 Windows UIA（每个格子是 `ButtonControl`，Name 里自带语义），识别准确率 100%，不用模板匹配或颜色阈值
- **决策**：确定性规则 + 子集差分 + 按约束连通分量做概率枚举，全程 < 2 ms
- **执行**：开格走 UIA `InvokePattern`（不碰鼠标）；插旗 / chord 走鼠标（UIA 没有对应通道）
- **速度**：单步 ~100 ms。三层读取收缩——边界格 → 焦点九宫格 → 读到空白格才按需展开；chord 批量连点，一次读盘打多个
- **录屏**：`录屏.bat` 用 ffmpeg 抓窗口，60 fps，产出可直接拖进度条的 MP4
- **GUI**：tkinter 深色控制台，实时指标 + 彩色日志 + 急停
- **打包**：`扫雷AI.exe` 单文件（自带扫雷程序），拷到别的电脑就能跑

## 快速开始

```bash
python agent.py --dry          # 只算不点，先看决策对不对
python agent.py --loop 5       # 实点，最多 5 局（输了自动重开）

python 扫雷控制台.bat           # 双击这个开 GUI 控制台
```

## 实测数据

| 项目 | 数值 |
|---|---|
| **单步耗时** | **~105 ms**（click ~65 + read ~30 + 等待/决策 ~5） |
| 一局（230 步中位） | **~24 s** |
| UIA 枚举 480 格 | 8 s（开局一次；**每次开新局还要再来一次**，见下） |
| solver 全套 | < 2 ms |
| **连打 100 局胜率** | **34.0%**（34 胜 / 60 负 / 6 作废；95% CI 24.7%~43.3%） |
| 剔除作废局 | **36.2%**（34/94） |
| 离线模拟（同策略，1000 局） | 首点随机安全格 **24.4%** / 首点必为 0 格 **42.1%** |

> **那 6 局「作废」不是输了**，是这台机器上别的程序（Excel / QQ / Everything / 终端 /
> 浏览器）抢走了前台焦点，插旗走真实鼠标就全打到别处去了，连续 3 轮触发熔断。
> 已修：抢不到前台时不再硬插，退回「只用 UIA invoke 开格」（开格不依赖焦点），
> 整局能继续。

> 离线模拟的数字要看首点规则：真实扫雷的首点**保证是 0 格**（游戏会把雷挪开），
> 一次大连锁；而 `play_sim.py` 原来是「随便点一个安全格」，多半只开 1 格。
> 所以老 README 里那个 **26.7% 既不是上限、也不是公平对比** —— 实机 34% 比它高，
> 而按真实规则重跑是 42.1%。实机比 42.1% 低约 8 个点，差在自动化开销
> （丢焦点作废、偶发 chord 失效），不在求解器。

> 新局开始后 UIA 元素引用会失效（`CurrentName` 一直返回上一局的旧数据），
> 所以两局之间必须重新枚举一次（8 s）。不这么做的话第二局必挂——插旗校验读到旧名字，
> 判定"没插上"后补标反而把旗取消了，最后触发熔断。

## 录屏

```bash
python record.py                # 录到运行 停录.bat 或按 Ctrl+C
python record.py --seconds 30   # 只录 30 秒
python record.py --fps 30       # 改帧率
python record.py --hw           # 硬件编码（自动试 qsv/nvenc/amf）
```

或双击 `录屏.bat` / `停录.bat`。产出在 `record/`。

**停止方式决定文件能不能用**——这是 `record.py` 存在的主要理由：

| 停止方式 | 结果 |
|---|---|
| 送 `q` 让 ffmpeg 自己收尾 | ✓ 全片解码零错误 |
| `taskkill /f` 强杀 | ✗ 最后一个分片截断，解码报 `Invalid NAL unit size` |

所以别直接 kill ffmpeg；`停录.bat` 只是建一个 `record\STOP` 标志，由 `record.py`
转成 `q` 送进去。另：抓取按窗口标题（`title=扫雷`），跟着窗口走，也不受 DPI 缩放影响。

**开销**：实测**基本不影响 AI 速度** —— 同一个脚本连打 3 局，不录时 98 / 99 / 109 ms
每步，边录边打是 101 / 98 / 102 ms 每步。编码器只占 0.87 个核（`--hw` 用 qsv 降到
0.64 个核），大头是 gdigrab 每帧一次全窗口 BitBlt + RGB→YUV 转换。

**实测素材**：`record/扫雷-*.mp4`，3 分 08 秒 / 11296 帧 / 60 fps / drop=0 / 44 MB，
期间 AI 打了 3 局（赢 1 局）。

**编码器选择**：默认 `libx264 -preset ultrafast -crf 18`。硬件编码省约 0.2 个核，
但同样 3 秒画面 libx264 出 0.85 MB、qsv 只出 0.23 MB —— 屏幕内容（数字笔画）
对压缩更敏感，追求清晰就别用 `--hw`。

## 说明

高级局（30×16 / 99 雷）存在约 5 次"信息不足必须猜"的位置——这是扫雷本身的数学限制。

**默认就是赌**：无确定步时用概率枚举挑风险最低的格子。
**连打 100 局实测胜率 34.0%**（34 胜 / 60 负 / 6 局因焦点被抢作废）；剔除作废局 36.2%。

想改成保守模式（无确定步就停手、不盲目乱点）加 `--no-guess`——那样那 5 次猜测会变成
「停在这里」，不踩雷也打不完一局。

同一个 solver 的离线模拟（1000 局）按**真实首点规则**跑是 42.1%，实机低约 8 个点——
差在自动化开销（丢焦点作废、偶发 chord 失效），不在求解器。
